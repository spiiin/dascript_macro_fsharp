# Бенчмарки ReactiveX

Зафиксированный локальный запуск: [RESULTS.md](RESULTS.md).

Из корня репозитория:

```powershell
./reactivex/run_benchmarks.ps1 -Mode All
# Отдельные режимы:
./reactivex/run_benchmarks.ps1 -Mode Interpreter
./reactivex/run_benchmarks.ps1 -Mode Jit
./reactivex/run_benchmarks.ps1 -Mode Aot
```

Требуется SDK daScript с JIT и CMake-пакетом. Для AOT также нужны CMake и
Visual Studio 2022 C++. `-Daslang` выбирает компилятор вместе с его SDK.
AOT собирает и исполняет Release-хост с `fail_on_no_aot` и проверкой
`main->aot`; генерация C++ сама по себе успехом не считается.
Используется существующий каталог сборки Rx AOT. После бенчмарка обычный
`./reactivex/run_aot.ps1` восстановит полный список тестов в этой сборке.

## Сценарии

| Сценарий | ReactiveX | Ручной эквивалент | Единица |
|---|---|---|---|
| range | range → subscribe | цикл и сумма | входной элемент |
| map | range → map → subscribe | преобразование и сумма | входной элемент |
| filter | range → map → filter → subscribe | преобразование, условие, сумма | входной элемент до фильтра |
| chain | range → map → filter → scan → subscribe | условие и накопитель в цикле | входной элемент до фильтра |
| subscribe | повторная подписка на готовый range из одного элемента | доставка одного значения и завершение | подписка |
| subscribe_chain | повторная подписка на готовую цепочку range → map → filter | преобразование одного значения и завершение | подписка |
| construct | создание и уничтожение range → map → filter, без подписки | конфигурация без runtime-узлов | цепочка |
| subject | Subject → map → subscribe | прямое преобразование и накопление | входное событие |
| subject_2 / subject_8 / subject_32 | Subject → map, 2 / 8 / 32 подписчика | преобразование и накопление для каждого слушателя | входное событие, до рассылки |
| reentrant_1 / reentrant_8 | первый callback отправляет следующий элемент в тот же Subject, 1 / 8 подписчиков | последовательный обход тех же значений | входное событие, до рассылки |
| reentrant_burst | callback каждого внешнего события добавляет восемь событий, 8 подписчиков | последовательность из девяти значений на внешний вызов | событие, включая восемь повторных |
| behavior / behavior_8 | BehaviorSubject → map, 1 / 8 подписчиков | начальное значение и последующие преобразования | входное событие |
| replay / replay_8 | ReplaySubject с историей 8 элементов, 1 / 8 подписчиков | начальная история и последующие преобразования | входное событие |
| replay_timed | ReplaySubject с историей 8 элементов, окном 1000 мс и 8 подписчиками | та же последовательность значений | входное событие |
| behavior_reentrant / replay_reentrant | первый callback добавляет следующий элемент, 8 подписчиков | начальная история и последовательный обход | входное событие |
| behavior_subscribe / replay_subscribe | подписка и отписка на готовом Subject → map, replay 1 / 8 элементов | обработка тех же начальных значений | подписка |

Ручной код — специализированный минимум для этого вычисления. Он не реализует
универсальную модель подписок, отмену, рассылку или защиту callback. Особенно
`construct`: ручная конфигурация может полностью оптимизироваться, поэтому
отношение времени к ней не является оценкой качества реализации Rx.
Разница показывает цену выбранной абстракции для конкретного сценария.

В каждом сценарии размеры 32, 512 и 4096, четыре пакета на замер, пять
повторов с чередованием порядка manual/Rx. Перед измерениями выполняется
прогрев. Итоговые суммы сравниваются в каждом парном замере; число завершений
проверяется отдельно. Для подписок проверяется закрытое состояние.
Порядок эффектов и обработку ошибок проверяют обычные тесты библиотеки;
эти бенчмарки измеряют успешную обработку `int`.

## Что измеряется

- Внутренний таймер охватывает только workload, без компиляции, прогрева и
  вывода CSV. Режимы исполняются последовательно. Время сборки/процесса
  записано отдельно и не входит в ns/unit.
- `heap_allocation_count` и `heap_allocation_stats()[0]` — накопительные
  выделения daScript heap: число и байты, включая впоследствии освобождённые.
  Отдельно записываются аналогичные счётчики string heap.
- `retained_bytes` — изменение живого daScript heap после уничтожения всех
  подписок и узлов; ненулевое значение приводит к ошибке. Это не пик памяти.
- Счётчики не включают нативный allocator, стек, LLVM, системные ресурсы или
  выделения компилятора. Поэтому «0 выделений» относится только к этим heap.
- `range/map/filter/chain` включают создание и закрытие одной цепочки на
  пакет. `subject` включает одну цепочку на весь замер. При росте размера
  постоянная настройка амортизируется. Сравнивайте все размеры, чтобы отличать
  настройку от расходов на каждое событие.
- `subscribe` и `subscribe_chain` исключают создание дескриптора из повторяемой
  операции: он создаётся один раз внутри замера. Последующее закрытие каждого
  экземпляра подписки входит в измерение.
- Добавочную цену оператора можно оценить сравнением `map−range`,
  `filter−map`, `chain−filter`; это разность полных сценариев, не изолированная
  стоимость вызова функции. Последние два сценария также меняют количество
  доставленных значений. Фильтр нормирован на вход, не на выход.

## Отчёты

По умолчанию `.work/benchmarks/{interpreter,jit,aot}` содержит `raw.log`,
`samples.csv` и `summary.json` (медиана, минимум/максимум времени, расходы
памяти на единицу, параметры, CPU/ОС, хеши компилятора и исходников).
AOT дополнительно сохраняет журнал сборки и результат строгого исполнения.
Для стабильных чисел повторяйте запуск на незагруженной машине; пороги времени
не используются как тест корректности. Замеры с почти пустым ручным циклом
особенно чувствительны к оптимизациям и точности таймера.

## Оптимизация Subject

Обычный Subject доставляет нерекурсивный `next` напрямую, без временной записи
очереди. Для одного слушателя снимок не нужен; для нескольких переиспользуется
буфер указателей. На время рассылки источник и все observers удерживаются
счётчиками ссылок, без выделения iterator lease.
Для последовательного потока `int` через `map` это устраняет выделения heap
на событие; настройка, подписка и завершение по-прежнему требуют памяти.
В столбце allocations/unit остаётся их амортизированная стоимость.

Повторные вызовы из callback остаются в очереди. Живая рассылка BehaviorSubject
и ReplaySubject также переиспользует снимок слушателей. Значения с финализаторами
и терминальные уведомления используют прежний путь доставки.
Для строк сохраняется копия входного значения в string heap.
Исключения и отписка сохраняют прежнюю семантику; отдельный
`test_subject_dispatch.das` проверяет отсутствие выделений в обычном пути,
повторный вход, удаление дескрипторов и события из финализатора.
`test_subject_fanout.das` проверяет ноль выделений после подготовки буфера
для 2, 8 и 32 слушателей, отписку, рост списка и порядок освобождения снимка.
При извлечении обычных `next` из очереди Subject теперь использует тот же
буфер снимка. Очередь сохраняет FIFO и переиспользует уже выделенную ёмкость;
рост очереди или числа подписчиков может потребовать дополнительных выделений.
Терминальные уведомления сохраняют прежний путь доставки.
`test_subject_reentrant.das` проверяет длинные цепочки и пачки повторных событий
для 1, 8 и 32 подписчиков, ошибки и время освобождения owning captures.
Буфер хранит только пустые указатели между рассылками; подписчиков и их данные
он не удерживает. Его ёмкость переиспользуется до удаления Subject, поэтому
расход памяти включает буфер пропорционально максимальному размеру снимка.

Сравнение до/после: [SUBJECT_OPTIMIZATION.md](SUBJECT_OPTIMIZATION.md).
Рассылка нескольким слушателям: [SUBJECT_FANOUT_OPTIMIZATION.md](SUBJECT_FANOUT_OPTIMIZATION.md).
Повторные события из callback: [SUBJECT_REENTRANT_OPTIMIZATION.md](SUBJECT_REENTRANT_OPTIMIZATION.md).

В BehaviorSubject и ReplaySubject replay по-прежнему клонирует отдельный снимок
истории: вызовы пользовательского clone сохраняются, в том числе для массивов.
Для POD-значений без финализатора пустой буфер снимка после replay возвращается
в пул Subject; следующий replay может переиспользовать его ёмкость.
Вложенные replay используют разные буферы, а timed pruning не меняет уже
клонированные непрочитанные элементы. Между replay буферы логически пусты и не
удерживают payload-ресурсы. Для строк, не-POD значений и финализаторов остаётся
обычное создание и удаление снимка. Расходы создания подписок не исчезают:
после прогрева устраняется только повторное выделение массива истории.
`test_cached_subject_dispatch.das` проверяет отсутствие выделений в прогретой
рассылке и цепочках, актуальность Behavior value, вложенные replay, cached
terminal, pruning непрочитанной timed history и финализаторы копий payload.
`test_cached_subject_clone.das` проверяет пользовательский clone строк, его
ошибки, переопределение clone массива POD, вложенное клонирование и восстановление
блокировок массива после ошибки.
Сравнение: [CACHED_SUBJECT_OPTIMIZATION.md](CACHED_SUBJECT_OPTIMIZATION.md).

Создание подписок также сокращает служебные выделения: observers удерживают
состояние подписки встроенной ссылкой со счётчиком, без отдельного iterator.
Пересылка error/complete в обычных операторах удерживает downstream напрямую.
Публичный RxSubscription сохраняет автоматическую отписку при удалении;
внутренние ссылки только продлевают жизнь storage и сами не закрывают подписку.
Порядок cleanup и освобождения callback captures сохранён, включая исключения
и удаление публичного дескриптора внутри обработчика.
`test_subscription_ownership.das` проверяет эти случаи через цепочку map/filter,
порядок cleanup, break/continue и отсутствие роста живой памяти.
Сравнение: [SUBSCRIPTION_OPTIMIZATION.md](SUBSCRIPTION_OPTIMIZATION.md).

Обработчики map/filter теперь удерживают состояния напрямую, без временных iterator
leases; это сокращает выделения при подписке и повторные обращения к rx_state на событии.
Сравнение: [MAP_FILTER_OPTIMIZATION.md](MAP_FILTER_OPTIMIZATION.md).

## Простые операторы, длинные цепочки и очереди

`benchmark_extended.das` проверяет 15 сценариев на размерах 32, 256 и 1024:
scan, distinct, tap, take/skip и while-формы, pairwise, контрольный map,
цепочку из 11 операторов, переподписки и четыре очереди. На каждый размер
выполняются четыре пакета и пять повторов с чередованием ручного кода/Rx.
Контрольная сумма включает результат, побочные эффекты tap и завершения.

Очереди zip/concat_map/observe_on/delay дополнительно измеряются по фазам:
заполнение и опустошение. Настройка подписки вынесена за их таймеры.
LiveBytesAfterFill — прирост живого daScript heap к концу заполнения,
включая snapshot, payload и таймеры; это не пик памяти. Drain включает
complete и доставку накопленных событий. Scheduler использует виртуальные часы;
стоимость измеряется обычным таймером, без реального sleep.
После удаления всех владельцев проверяется возвращение heap к исходному размеру.

```powershell
./reactivex/run_extended_benchmarks.ps1 -Mode All
```

Для сравнения до/после сохраните перед изменением отдельный каталог с
`lib/reactivex.das`, `lib/rx_scheduler.das`, `lib/rx_payload_checks.das` и теми же
`benchmarks/benchmark_extended.das`, `benchmarks/extended_workloads.das`.
В текущем локальном запуске такой снимок лежит в `.work/simple-operators/baseline`.

```powershell
./reactivex/run_extended_benchmarks.ps1 -BaselineDirectory ./reactivex/.work/simple-operators/baseline -BuildOnly
# Дождаться завершения остальных тестов и сборок, затем:
./reactivex/run_extended_benchmarks.ps1 -BaselineDirectory ./reactivex/.work/simple-operators/baseline -RunOnly
```

Runner выполняет два последовательных раунда: before/after и after/before.
Ручной код и Rx чередуются внутри процесса. Interpreter, JIT и Release AOT
запускаются отдельно; AOT проверяет strict linking и main->aot=yes.
BuildOnly/RunOnly позволяют исключить параллельную сборку из замеров времени.
Дочерний benchmark-процесс по умолчанию закреплён за логическим CPU 0.
Параметр -Processor выбирает другое ядро; -Processor -1 отключает закрепление.
Affinity остальных процессов не меняется.
Проверяются хеши компилятора/исходников и совпадение benchmark до/после.
Измерение времени не включает компиляцию самого запускаемого скрипта;
стороннюю нагрузку ОС runner не контролирует.

`samples.csv`, `queue-samples.csv`, `summary.json` и исходные логи сохраняются
в `.work/extended-benchmarks` (либо OutputDirectory). Все нормированные значения
вычисляются из накопительных счётчиков daScript heap, а не native allocator.
Для очередей выводится цена входа/пары, для resubscribe — цена подписки.
Ручные реализации специализированы и не включают общий протокол Rx.

Тесты `test_simple_operator_ownership.das` и `test_extended_benchmarks.das`
включены в общий scripts.ps1 для interpreter/JIT и исполнения AOT.
Результаты оптимизации: [SIMPLE_OPERATORS_OPTIMIZATION.md](SIMPLE_OPERATORS_OPTIMIZATION.md).

Сокращение выделений на отложенное событие observe_on/delay, сохранение
порядка scheduler и регрессионные проверки владения:
[TIME_OPERATORS_OPTIMIZATION.md](TIME_OPERATORS_OPTIMIZATION.md).
