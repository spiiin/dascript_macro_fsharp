# observe_on и subscribe_on

Оба оператора используют существующий однопоточный RxScheduler. Потоки ОС не
создаются: приложение вызывает rx_tick, тесты — rx_advance_to/rx_advance_by.

```dascript
var inscope clock <- rx_virtual_scheduler()
var inscope source <- rx_defer(@() {
    print("подключение\n")
    return <- rx_range(1,3)
}) |> rx_subscribe_on(clock) |> rx_observe_on(clock,rx_queue(3))

var inscope subscription <- rx_subscribe(source,
    @(n:int) {print("значение {n}\n")},
    @(message:string) {print("ошибка: {message}\n")},
    @() {print("готово\n")})

// До этого вызова источник не подключён, callbacks не выполнены.
rx_advance_to(clock,0)
```

## Правила исполнения

| | observe_on | subscribe_on |
|---|---|---|
| Подключение upstream | Немедленно | Запланированное действие с задержкой 0 |
| next/error/complete | Отдельные действия с задержкой 0, в порядке входных событий | В контексте вызова upstream, без дополнительного переноса |
| Отписка | Немедленно закрывает upstream и отменяет ожидающие уведомления | Немедленно отменяет ожидающее подключение или закрывает подключённый upstream |
| Закрытие часов | Сбрасывает очередь, сообщает `rx scheduler closed`, освобождает upstream | До подключения: ошибка и отмена запуска. После подключения: часы больше не управляют жизнью upstream |

Сочетание операторов откладывает и подключение, и доставку. Порядок операторов
имеет значение: эффекты до observe_on выполняются при производстве событий,
эффекты после него — при выполнении запланированных уведомлений.
Задержка 0 не вызывает callback прямо из subscribe или producer. Действие,
созданное во время tick/advance, может выполниться в том же вызове, если остаётся
бюджет max_actions. Для пошагового исполнения передайте max_actions=1.

Отписка намеренно не планируется: ресурсы освобождаются без следующего tick.
Отмена до запуска subscribe_on не вызывает defer-фабрику. Холодный источник
подключается отдельно для каждого подписчика; состояние очереди observe_on также
отдельное. Планировщик удерживается через стандартную непервичную ссылку.

## Ограниченная очередь observe_on

Перегрузка без настроек использует `rx_queue(256,RxOverflowPolicy.error)`.
Явная ёмкость должна быть положительной; unbounded-режима нет. Ограничение
считает ожидающие next, но не выполняющийся callback и не terminal. Complete
или error занимает отдельное завершающее действие и не вытесняет значения.

| Политика | При заполнении |
|---|---|
| error | Закрыть upstream, уничтожить ожидающие значения, запланировать единственную ошибку `rx_observe_on: queue overflow` |
| drop_oldest | Уничтожить самый старый ожидающий next и сохранить новый |
| drop_latest | Отбросить входной next, сохранив очередь |

Обычный upstream on_error, включая пустое сообщение, следует после уже принятых
значений. Это отличается от rx_delay, где ошибка немедленная и сбрасывает
ожидающие значения. Очередь не является backpressure; producer продолжает работу.
Настройки ограничивают число элементов, а не размер payload в байтах.

Payload соответствует общему контракту Rx: copyable owning значения. Строки
сохраняются снимками. Вытеснение и отмена немедленно освобождают сохранённые
payload. В текущей реализации каждый принятый next имеет отдельное действие
планировщика; отдельного постоянного worker-потока или общего drain-цикла нет.

## Ошибки и очистка

on_error — уведомление потока. Исключение из observer callback или teardown
остаётся исключением: подписка закрывается, ожидающие действия удаляются,
исключение распространяется вызывающему коду. Закрытие планировщика сообщает
ошибку синхронно в процессе закрытия, поскольку исполнять очередь уже нельзя.
Исходный ресурс может освободиться до доставки terminal: observe_on задерживает
уведомления, а не закрытие завершившегося upstream.

Эти операторы не обеспечивают передачу событий между потоками. Вызывать источник,
подписки и планировщик нужно в одном потоке/контексте.

`-Jit`, затем `./reactivex/run_aot.ps1`.
