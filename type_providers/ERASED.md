# Стирание и ленивое раскрытие

Это учебная реализация **стираемых типизированных выражений**, а не полная
реализация first-class erased types F#. Работает на штатных макросах Daslang
0.6.4, без изменения компилятора и без C++-плагина.

```powershell
cd C:\src\dascript_macro_fsharp\type_providers
.\run.ps1
.\run.ps1 -Test
.\measure_lazy.ps1 -Count 10000
```

Скрипты принимают `-Daslang <путь к daslang.exe>`. Для прямого запуска:

```powershell
daslang.exe erased_demo.das -no-module-cache
daslang.exe erased_demo.das -no-module-cache -log
```

## Использование

```das
let leader : string = erased(node, "schemas/world", "Player", _.team.leader.name)
let health : int = erased(node, "schemas/world", "Player", _.health)
```

`node` — уже разобранный JSON. Два строковых литерала задают каталог схем
и исходный виртуальный тип. Последний аргумент — ограниченный DSL:
только цепочка обращений к полям от `_`. Это обычный AST `ExprField`,
но макрос сам проверяет его по внешним схемам до стандартного вывода типов.

Внутри селектора компилятор-макрос знает:

```text
_ : Player
_.team : Team
_.team.leader : Player
_.team.leader.name : string
```

Опечатка `_.team.leader.naem`, продолжение `_.health.name` и присваивание
результата `_.health` переменной `string` отклоняются при компиляции.

## Что стирается

После раскрытия компилятор видит эквивалент:

```das
let leader : string = ep_string(
    ep_object(
        ep_object(ep_root(node), "team", "Player.team"),
        "leader", "Player.team.leader"),
    "name", "Player.team.leader.name")
```

Имена виртуальных типов могут остаться в диагностических строках, но
никаких структур `Player`/`Team`, их конструкторов или runtime-описателей
провайдер не создаёт. Все объектные значения представлены `JsonValue?`.
Скалярный результат имеет настоящий тип `string`, `int` или `bool`.
Исходное выражение `node` вычисляется один раз на макровызов, даже если оно
является вызовом функции с побочным эффектом; это проверено в демо.

Результат-ссылка заимствован из исходного JSON-дерева. Не освобождайте
корень, пока используете такие ссылки, и не вызывайте `delete_json` на
заимствованной ветке. Демо освобождает владельца один раз через `finally`.

## Что раскрывается лениво

Каждый тип хранится отдельно: `schemas/world/Player.json`, `Team.json`, ...
Поле-ссылка записывается так:

```json
{ "name": "team", "type": "ref", "target": "Team" }
```

Макрос не перечисляет файлы каталога и не обходит все ссылки рекурсивно.
Для `_.name` нужен только `Player.json`. Для `_.team.title` добавляется
`Team.json`. Для `_.team.leader.name` снова используется уже загруженный
`Player.json`. Цикл `Player -> Team -> Player` допустим: обход ограничен
конечным селектором, а не размером достижимого графа.

Если селектор заканчивается на `_.team`, схема `Team` пока не нужна:
результат — объектный JSON-view. При переходе к полю `Team` она загружается.
Сами описания полей внутри одного загруженного файла разбираются целиком;
ленивость здесь на уровне файлов типов и разрешения целевых типов/используемых
членов, а не потокового чтения каждого поля JSON-схемы.

В `Player.json` намеренно есть ссылки на повреждённую `Broken.json`,
отсутствующую `NotDownloaded.json` и поле с неподдерживаемым типом.
Основное демо работает, пока эти члены не используются. Отдельные тесты
обращаются к ним и получают ожидаемые ошибки компиляции.

Кеш описаний хранится в экземпляре compile-time макроса. При повторном
чтении той же схемы в этой компиляции файлового I/O нет. Скрипты запускают
компилятор с `-no-module-cache`, чтобы межзапусковый AST-кеш не скрывал
изменения внешних JSON-файлов. Полноценной интеграции зависимостей с системой
сборки в этом примере нет.

## Проверка пространства из 10 000 типов

`measure_lazy.ps1` создаёт временный каталог из `Node0.json` ...
`Node9999.json`. Каждый тип ссылается на следующий; последний замыкает цикл.
Программа читает `_.id` и дважды `_.next.id` от `Node0`.

Проверено: только два сообщения `[erased.load]`, для `Node0` и `Node1`.
Размер объявленного пространства — 10 000; загружено схем — 2;
создано номинальных типов — 0. Временные файлы после проверки удаляются.
Вывод времени охватывает запуск компилятора, компиляцию и выполнение;
он не является измерением скорости чтения отдельных полей.

## Производительность и повторные проверки

| Действие | Первый, generative-пример | Erased-пример |
|---|---|---|
| Чтение схемы | При компиляции | При компиляции, только нужные типы |
| Представление данных | Структура с нативными полями | Исходное JSON-дерево |
| Проверка данных | При заполнении структуры | При чтении каждого выбранного пути |
| Повторное чтение `health` | Прямой доступ к полю `int` | Поиск ключа JSON и проверка значения |
| Неиспользуемые поля | Все поля структуры загружаются | Доступ к ним не генерируется |

Стирание само по себе не требует динамической проверки каждого доступа.
Здесь такая стоимость возникает из выбранного представления `JsonValue?`
и проверяющих аксессоров. Провайдер с представлением в виде проверенного
массива мог бы генерировать обращения по заранее известным индексам.
Потеря виртуального имени типа у обычной переменной — отдельное ограничение
этого DSL; она не заставляет runtime читать схему заново.

Для горячего участка можно один раз извлечь нужный скаляр:

```das
let health : int = erased(node, "schemas/world", "Player", _.health)
// Дальше используем health: больше ни поиска JSON-ключа, ни проверки его типа.
let after_damage = health - 10
```

Это снимок значения: изменение JSON позже его не обновит. Для большого числа
повторно читаемых полей предпочтительнее первый пример с материализацией
структуры. Erased-пример удобен для выборочного чтения нескольких полей из
большого пространства схем. Само JSON-дерево здесь всё равно разбирается
целиком: ленивость типов не означает ленивую загрузку данных.

## Ограничение относительно F#

```das
var team : JsonValue? = erased(node, "schemas/world", "Player", _.team)
let title = erased(team, "schemas/world", "Team", _.title)
```

Во второй строке `Team` приходится указать явно. Обычная система типов
daScript не помнит, что `team` получен из `Player.team`; указание другой
схемы здесь будет новой явной интерпретацией JSON. У F# виртуальные типы
сохраняют статическую идентичность при передаче переменных и аргументов
до стадии стирания. Наш макрос проверяет типы только внутри каждого селектора.

Следовательно, это реальное стирание выражений, но **не номинальная
типобезопасность между произвольными переменными/функциями**, не IDE-провайдер
и не автоматическое раскрытие произвольного `variable.field` вне DSL.
Структура-оболочка с указателем могла бы сохранять номинальный тип в daScript,
но тогда она оставалась бы настоящим типом, что уже другой компромисс.

Runtime-валидация частичная: проверяются только посещённые объекты и значения.
Она не доказывает соответствие всего документа схеме. Ошибка данных вызывает
`panic` с путём поля; ошибка схемы или селектора — ошибку компиляции.

## Где читать код

- `erased_provider.das`: кеш схем, обход `ExprField`, проверка виртуальных
  типов и генерация выражения через `qmacro`.
- `erased_runtime.das`: обычные проверяющие аксессоры к JSON.
- `erased_demo.das`: скаляры, вложенные ссылки, цикл схем, однократное
  вычисление корня и объектный результат без proxy-структуры.
- `test_erased_*.das`: положительные и отрицательные сценарии.
- `run.ps1 -Test`: дополнительно проверяет раскрытый код через `-log`.

Точка расширения: `AstCallMacro.canVisitArgument()` оставляет последний
аргумент невыведенным; `visit()` получает его исходный AST, проверяет
виртуальные поля и возвращает новый AST. После этого обычный компилятор
проверяет настоящий тип результата и совместимость runtime-вызовов.
