# CoroutineBuilder

Кооперативные игровые сценарии с паузами по кадрам. Отдельный модуль использует
генераторный протокол CE и общую защиту итераторов, без изменений макроса.

```das
require ./lib/computation_macro.das
require ./lib/coroutine_builder.das

var inscope task <- computation(CoroutineBuilder()) {
    print("start\n")
    yield next_frame()
    print("next frame\n")
    yield wait_frames(2)
    print("finished\n")
}

// Вызывать один раз за кадр игрового цикла:
let active = coroutine_resume(task)
// Для отмены:
coroutine_cancel(task)
```

Создание task не выполняет тело. `coroutine_resume` работает синхронно до
следующей границы кадра или завершения. Возвращает `true`, если сценарий
приостановлен, и `false`, если завершён. После завершения/отмены повторные
resume возвращают false; повторная отмена безопасна.

## Точное время ожидания

Если первый resume дошёл до `yield wait_frames(2)`, он возвращает true.
Второй resume тоже возвращает true без выполнения следующего оператора тела.
Третий продолжает тело после ожидания. `next_frame()` эквивалентен
`wait_frames(1)`. `wait_frames(0)` не приостанавливает выполнение; отрицательное
число вызывает panic. Это число вызовов resume, а не миллисекунды.

Публичный task — владеющий однопроходный `iterator<CoroutineFrame>`.
Его можно перемещать, но не копировать. Храните его в `var inscope ... <- ...`
либо явно вызывайте cancel. Повторный запуск создаётся новым вызовом фабрики
или через deferred.

## Пайпы, циклы и дочерние сценарии

```das
var inscope task <- computation(CoroutineBuilder()) {
    let waypoint = fixed_array(10,20) |> bind
    print("move to {waypoint}\n")
    yield wait_frames(2)
}
```

Bind сохраняет семантику Sequence: выполняет продолжение для каждого элемента
источника. Пауза задаётся `yield`; `next_frame() |> bind` не является await.
Поддерживаются `for`, `while`, ветвления и локальные переменные между кадрами.

`child() |> yield_from` последовательно выполняет дочерний CoroutineBuilder,
передавая его границы кадров наружу. После завершения child родитель продолжает
работать в том же resume до своей следующей паузы. Отмена и ошибка закрывают
вложенные источники изнутри наружу. См. `coroutine_demo.das`.

## Ресурсы и ошибки

`use_resource` и `try_finally` действуют до выхода из своего блока, а не до
ближайшего yield. Поддерживаются move-only ресурсы через `var resource &`.
При завершении, отмене, native break при обходе и исключении внутри сценария
итераторы закрываются. Исключение из resume пробрасывается вызывающему коду,
а сам task после этого закрыт. Обработку внутри сценария можно задать try_with.
Освобождающие функции должны быть небросающими; сохраняются ограничения runtime
из `SEQUENCE_RESOURCES.md` и `MOVE_RESOURCES.md`.

Исключение игрового кода между вызовами resume библиотека перехватить не может:
вызывающий код должен закрыть принадлежащие ему задачи. Для планировщика
используйте coroutine_scope из coroutine_scheduler. Для native for с
бросающим потребителем действуют ограничения Sequence; используйте защищённый
`sequence_each` или явное закрытие в recover.

## Deferred и границы первой версии

`deferred(CoroutineBuilder(), data) $(snapshot) { ... }` сохраняет снимок данных.
Каждый `run_deferred` создаёт отдельный сценарий, удерживающий свой снимок до
закрытия. Сохранённое вычисление можно удалить до завершения его запусков.
Прямые захваты указателей в обычном CE не продлевают жизнь их целей.

Здесь нет фоновых потоков, асинхронного I/O, ожидания секунд, передачи delta time,
вытесняющего планирования или результата через return. Сценарий без достижимого
yield может занять весь вызов resume. Для планирования нескольких задач используйте модуль
coroutine_scheduler; игровой цикл вызывает его tick.

`test_coroutine.das` проверяет точные кадры, отсутствие раннего выполнения,
завершение, повторную отмену, ресурсы и память при break/ошибке, вложенные
сценарии и независимые deferred-запуски.

## Общий игровой tick

Модуль `coroutine_scheduler` управляет несколькими сценариями: spawn, tick,
cancel, терминальные статусы и ошибки. См. [COROUTINE_SCHEDULER.md](COROUTINE_SCHEDULER.md).
