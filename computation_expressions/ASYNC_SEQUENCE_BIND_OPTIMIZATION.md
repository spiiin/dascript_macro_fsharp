# AsyncSequence: объединение адаптеров Task bind

Оптимизация сохраняет `source |> bind`, порядок опроса и эффектов, отмену,
таймауты, deferred и владение move-only значениями. На один Task bind убраны
два heap-выделения и 128 байт служебных данных. Это измерение daScript heap,
без native/OS-памяти; постоянные расходы создания stream учитываются отдельно.

## Изменение раскрытия

Раньше стандартный Task адаптировался через `ce_await_source`, затем оборачивался
в `ce_sequence_input` либо `ce_sequence_own_elements`. Два generator означали
четыре выделения: по объекту lambda и iterator на каждый.

Теперь `ce_sequence_source` после определения типов узнаёт стандартный
`task_builder::ce_await_source` с дескриптором AsyncSequenceBuilder и выбирает
`ce_await_input`. Проверяется исходная generic-функция и номинальный тип builder,
а не строка имени уже сгенерированной функции. Другие builders и пользовательские
реализации `ce_await_source` продолжают использовать прежнюю защиту.

Один новый iterator владеет Task и стабильным слотом события, выдавая ссылку
на слот. Pending не продвигает продолжение; Succeeded переносит или копирует
результат и запускает продолжение один раз. Заимствование живёт до конца всего
продолжения, включая вложенный bind/yield. После `yield <- value` слот пуст.
Отмена передаёт сигнал Cancelled, а не обычный pending или исключение в try_with.
При ошибке опроса дочерний Task закрывается до запуска обработчика. При закрытии
iterator уничтожается слот результата, отменяется дочерний Task и передаётся
ошибка его cleanup, как в прежнем пути. Защита ресурсов остаётся включённой.

Пользовательский код не меняется:

```das
var stream <- computation(AsyncSequenceBuilder(type<array<int>>)) {
    var value & = task_after_polls_move(1,[7,8]) |> bind
    task_after_polls(1,0) |> bind
    yield <- value
}
```

## Измерения

SDK daScript 0.6.5-RC2, JIT без кеша. 1024 элемента × 8 запусков в sample,
9 samples; Work=0/32, Pending=0/1. Перед правкой сохранена отдельная копия кода,
после — вторая. В lib этих копий различаются только async_sequence_builder.das
и computation_macro.das. Сравнение использует тот же runner и те же workloads,
что и [первый этап оптимизации](ASYNC_SEQUENCE_PERFORMANCE.md).

Медианы основной серии при Work=0, Pending=0:

| Сценарий | Выделений/элемент до → после | Байт/элемент до → после | нс/элемент до → после |
|---|---:|---:|---:|
| next | 8,0166 → 6,0166 | 609,18 → 481,17 | 1348,85 → 958,86 |
| for | 18,0342 → 16,0342 | 1254,53 → 1126,52 | 2736,62 → 2555,31 |
| zip | 28,0732 → 24,0732 | 2021,46 → 1765,44 | 4938,06 → 4158,69 |
| and_bind | 12,0166 → 10,0166 | 993,18 → 865,17 | 2044,63 → 1576,88 |
| move (yield array<int>) | 9,0166 → 7,0166 | 721,22 → 593,21 | 1393,68 → 1034,42 |

zip содержит два Task bind на строку; and_bind адаптирует один объединённый Task.
Остаточный heap после каждой партии равен нулю, checksum CE и ручного кода совпал
во всех конфигурациях. Экономия выделений повторилась во всех samples, включая
Work=32 и Pending=1. Небольшая дробная часть байтов отражает фиксированные расходы
создания stream, амортизированные по числу элементов.

В основной серии медианы времени снизились на 6,6–28,9% в зависимости от сценария
и конфигурации. Это локальные микрозамеры polling, а не обещание ускорения сети.
В повторной серии нагрузка машины заметно изменилась: ручной next до правки
занял 1127 нс вместо 514 нс в основной серии. Поэтому большой выигрыш времени
повторной серии нельзя целиком приписывать оптимизации. Уверенный результат —
сокращение выделений; исходные времена и парные отношения CE/manual сохранены
полностью, включая шумные samples.

запустить тот же runner с `-SourceRoot <копия/computation_expressions>`.

## Проверки

В test_async_sequence_move добавлена проверка owning результата Task через
следующий pending bind: отмена до получения результата и после, закрытие stream,
ошибка продолжения и перенос результата наружу с последующим закрытием stream.
Повторные прогоны проверяют точное совпадение счётчиков владения и остаточного heap.
Существующие наборы покрывают grouped bind, async For/zip, deferred, таймауты,
ранний выход и ошибки cleanup. Исполнение в интерпретаторе, JIT и AOT проверяется
раздельно: 36 наборов в интерпретаторе, 9 в JIT и 9 собранных и исполненных
в AOT со строгой линковкой. Также прошли 14 проверок диагностик, 7 примеров и
5 базовых CE-наборов. [Результаты и хеши](async-bind-performance/validation/summary.json).

У async_sequence_demo исправлен существовавший и до оптимизации недостаточный
лимит определения типов: пример использует max_infer_passes=128, как другие
примеры со вложенными асинхронными producer/consumer.

Служебный iterator bind всё ещё создаётся. Простой Async For, owning-ячейки
вложенных областей и промежуточный stream zip остаются отдельными кандидатами
для следующих оптимизаций.
