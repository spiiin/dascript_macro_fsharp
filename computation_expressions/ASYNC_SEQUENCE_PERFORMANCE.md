# AsyncSequence: измерения и первая оптимизация

Это отчёт о снятии lease-итератора с каждого next. Последующая оптимизация
Task bind описана отдельно: [ASYNC_SEQUENCE_BIND_OPTIMIZATION.md](ASYNC_SEQUENCE_BIND_OPTIMIZATION.md).

## Воспроизведение

```powershell
./run_async_sequence_benchmarks.ps1
./run_async_sequence_benchmarks.ps1 -Jit -Elements 1024 -Batches 8 -Samples 9 -OutputDirectory .work/async-jit
./run_async_sequence_benchmarks.ps1 -Jit -Elements 2048 -Work 128 -OutputDirectory .work/async-larger
```

Параметры Elements/Batches задают длину stream и число его полных запусков в одном
sample. Work выбирает второй размер полезной работы: каждый процесс проверяет
0 и Work итераций целочисленного преобразования. Дополнительно проверяются 0 и
1 pending у первого Task; второй Task в zip/and_bind имеет вдвое больше pending.
Это вычислительные микробенчмарки polling, без сети, часов scheduler и ожиданий ОС.
Каждый результат участвует в int64 checksum. В тестах проверяется также независимый
ожидаемый checksum, включая пустые stream, разные размеры работы и pending.

| Сценарий | CE | Ручной вариант |
|---|---|---|
| next | Производитель с Task bind на элемент, чтение через next | Нативный generator и явный task_poll |
| for | Async For по такому источнику, преобразование элемента | Явный цикл next/poll/take |
| zip | Async For по двум источникам, преобразование пары | Явный совместный опрос двух next, остановка по кратчайшему |
| and_bind | Два Task на элемент через and_bind | Тот же task_when_all, явный poll/take |
| move | Task bind и выдача array<int> перемещением | Нативный generator с тем же переносом массива |

Обе стороны используют один AsyncSequence/Task API для хранения stream и next.
Ручные варианты специализированы под успешные пути этих задач; это не альтернативный
универсальный builder и не сравнение с голым iterator без владения. Ошибки, отмена,
таймауты и финализаторы проверяются функциональными наборами отдельно.

Прогрев выполняется до измерений; CE/manual чередуются между samples. Время снято
внутри программы, без компиляции, запуска процесса и печати. JIT cache и module cache
отключены. Нельзя выполнять тяжёлые сборки/тесты параллельно с замерами времени.

Сохраняются raw.log, samples.csv и summary.json с хешами SDK и исходников, параметрами,
медианами и диапазонами. SourceRoot позволяет измерять независимую сохранённую копию.
CompilationAndProcessMs включает весь процесс и не является чистым временем компиляции.
Счётчики heap_allocation_count/heap_allocation_stats()[0] накопительные: освобождение
не уменьшает их. RetainedBytes после партии обязан быть нулём. Это не пик памяти;
строковый heap, LLVM, native/OS-выделения сюда не входят. Размер элемента и число
итераций влияют на результат, постоянные расходы создания stream амортизируются.

## Что показало раскрытие

Минимальный пример для просмотра `-compile-only -log`:
[async_sequence_expansion.das](benchmarks/async_sequence_expansion.das).

1. `bind` ожидает Task через ce_await_source, затем защищённый iterator входа.
   В данном workload это четыре дополнительных heap-выделения на bind относительно
   ручного polling: closure и iterator адаптера, closure и iterator защитного входа.
2. Async For хранит весь элемент/zip-строку в owning-ячейке итерации. Она нужна
   для безопасных захватов во вложенных bind, use_resource и try_finally. Область
   содержит ячейку, cleanup lambda, генератор тела, генератор scope и защитный вход:
   ещё восемь выделений на итерацию в скалярном workload. Замена такой области
   обычной ссылкой уже нарушала захват move-only данных вложенными генераторами.
3. Zip создаёт промежуточный stream пар; каждый его элемент также читается через next.

Таким образом, основная разница с ручным кодом остаётся в универсальных адаптерах
ожидания и защищённых областях владения. Пайповый синтаксис сам по себе не объясняет
эти расходы. Нативные циклы по range/массивам не становятся async For.

## Что оптимизировано

Раньше каждый next создавал два генератора: собственный и отдельный lease-генератор,
который удерживал учтённую ссылку на heap-состояние. Теперь её удерживает и освобождает
финализатор самого next. Из раскрытия исчезли поле lease в его closure, вызов
ce_async_sequence_lease(state,false) и удаление этого iterator.

Убраны **два heap-выделения и 128 байт на каждый next** на измеренном SDK Windows x64,
включая завершающий запрос none. Владелец stream по-прежнему закрывает производителя
немедленно; ожидающий next удерживает состояние до собственного завершения/удаления.
Удаление неопрошенного next также вызывает finally и освобождает ссылку. Доставленные
move-only значения продолжают принадлежать потребителю независимо от stream.

Исходники before/after различаются только этой правкой async_sequence_builder.das.
Для восстановления исходной версии в отдельной копии сохранён
[патч before → after](async-performance/next-reference-optimization.patch): применить
его в обратную сторону к копии проверенной версии. `-SourceRoot` задаёт эту копию
runner. Все остальные lib-файлы и оба измеряемых workload совпадали.

## Результаты

SDK v0.6.5-RC2, Windows x64. Полные параметры и хеши — в
[comparison.json](async-performance/comparison.json) и summary.json каждого запуска.
Основная серия: 1024 элемента, 8 stream на sample, 9 samples, Work=0/32, Pending=0/1.
Ниже Work=0, Pending=0, число выделений **на выданный элемент всего сценария**,
включая производство, Task bind и потребление. Это не число выделений одной функции next.

| Сценарий CE | Выделений до → после | Байт до → после |
|---|---:|---:|
| next | 10.02 → 8.02 | 737.30 → 609.18 |
| for | 22.04 → 18.03 | 1510.78 → 1254.53 |
| zip | 36.08 → 28.07 | 2533.96 → 2021.46 |
| and_bind | 14.02 → 12.02 | 1121.30 → 993.18 |
| move | 11.02 → 9.02 | 849.35 → 721.22 |

Снижение проверено точно для всех 360 пар samples, обоих вариантов CE/manual,
размеров работы и pending. Для каждого stream учитывается дополнительный terminal next.
Ручные варианты также используют изменённый next и экономят память: после
оптимизации их счётчики составляют соответственно 4.01, 6.01, 10.02, 8.01 и 5.01.
Более короткие серии с 512 элементами подтверждают амортизацию постоянных расходов.

Для времени результат менее определённый. Медиана CE next между отдельными JIT-процессами
менялась от 1536 до 3017 нс до правки и от 1375 до 2377 нс после; нагрузка машины заметна.
В обратном сравнении after-jit-repeat → before-jit-bracket получено:

| Сценарий CE | До, нс/элемент | После, нс/элемент | Изменение времени |
|---|---:|---:|---:|
| next | 1536 | 1375 | −10.5% |
| for | 3136 | 2978 | −5.0% |
| zip | 5868 | 5347 | −8.9% |
| and_bind | 2232 | 2379 | +6.6% |
| move | 1626 | 1531 | −5.8% |

Эта таблица — наблюдение одного обратного прохода, не доказательство универсального
ускорения. В частности, and_bind в нём медленнее. Более ранняя серия давала ухудшение
всех времён после правки, повторная — обратную картину. Все эти результаты сохранены,
а не отброшены. Уверенный результат здесь — уменьшение аллокаций при сохранении
контракта; для вывода о времени нужны повторения на спокойной машине.

## Проверки оптимизации

Тест [test_async_sequence_benchmarks.das](tests/test_async_sequence_benchmarks.das)
включён в `run_computation.ps1 -Test`: сравнивает CE/manual с ожидаемым checksum
на пустых и непустых входах, нескольких размерах работы и pending, затем проверяет
остаточный heap после прогрева. Порогов времени в тесте нет.

После правки проверены 27 Task-наборов, восемь функциональных AsyncSequence-наборов
и этот тест в интерпретаторе; восемь AsyncSequence-наборов и тест workload — в JIT.
Те же девять AsyncSequence/workload тестов собраны и исполнены в AOT-хосте со строгой
линковкой и проверкой main->aot. Они покрывают неопрошенные next, удаление владельца
с pending next, отмену/таймаут, ранний выход, ошибки, deferred и move-only значения.
[AOT summary и логи](async-performance/validation/aot-summary.json).

Для manifest с test_async_sequence_benchmarks AOT-хост дополнительно генерирует
библиотеку async_sequence_workloads; для остальных manifest она не подключается.
Это нужно для AOT-линковки импортированных nongeneric функций workloads, а не для
самого AsyncSequenceBuilder.

## Следующие кандидаты

Объединение адаптера Task bind и защитного входа выполнено в следующем шаге;
см. [отдельный отчёт](ASYNC_SEQUENCE_BIND_OPTIMIZATION.md). Следующий кандидат —
специализация простого Async For без захватов и вложенных ресурсных областей.
Безусловно убирать owning-ячейку итерации нельзя: это меняет время жизни заимствований
и захватов. Оптимизации zip без промежуточного next также должны сохранять кратчайший
источник, порядок эффектов и закрытие частично готовой строки.
