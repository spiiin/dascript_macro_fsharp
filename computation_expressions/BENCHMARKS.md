# CE против ручного кода

Выделения памяти, время компиляции и размер раскрытия: [PERFORMANCE_METRICS.md](PERFORMANCE_METRICS.md).
AsyncSequence: next, Async For, zip, and_bind и move-only элементы, счётчики памяти
и сравнение до/после: [ASYNC_SEQUENCE_PERFORMANCE.md](ASYNC_SEQUENCE_PERFORMANCE.md).

```powershell
./run_benchmarks.ps1
./run_benchmarks.ps1 -Jit -OutputDirectory ./benchmark-results-jit
```

Параметры: `-Daslang`, `-Iterations` (по умолчанию 200000 операций в одном
замере), `-Samples` (9), `-Jit`, `-OutputDirectory`. Без Jit используется
интерпретатор. Ошибка JIT завершает runner; скрытого переключения на
интерпретатор нет. Требуются PowerShell и тот же daslang, что для примеров.

## Что измеряется

| Сценарий | Одна операция | Ручной вариант |
|---|---|---|
| result_mixed | Три Result bind с остановкой при ошибке | Те же проверяющие функции и явные проверки тегов |
| state_loop | 16 обновлений State и итоговый результат | Локальная переменная, 16 обновлений и тот же формат результата |
| state_variable | Число итераций `(seed*13)%97`, нелинейное обновление State | Прямой цикл с тем же обновлением |
| list_product | Два bind по 4 элемента, материализация 16 результатов и контрольная сумма | Два вложенных цикла с добавлением в один массив |
| sequence_protected | Создание, чтение 32 элементов, закрытие итератора | Нативный generator с тем же ce_sequence_protect и sequence_each |

Ручной код выполняет ту же полезную работу и имеет тот же наблюдаемый результат,
но не имитирует внутренние временные объекты CE. Например, List CE может
создавать промежуточные массивы, а ручной цикл пишет сразу в итоговый массив.
Для Sequence обе стороны используют защитные обёртки: это сравнение CE и
ручного генератора при одинаковом контракте закрытия, а не цена самой защиты.

Исходники всех пар — `benchmark_workloads.das`. Тест
`test_benchmark_workloads.das` сравнивает контрольные суммы для всех 64 входов и
проверяет отсутствие остаточного роста heap. Он включён в обычный test runner;
временные пороги в тестах корректности не используются.

## Методика

1. Бенчмарк компилируется и запускается один раз для выбранного режима.
2. Перед каждой парой — 1000 прогревочных операций каждого варианта.
3. Внутри измеряемого цикла меняется seed от 0 до 63, результат накапливается
   в int64 и выводится. У Result присутствуют и успешные, и ошибочные пути.
4. Для каждого повторения чередуется порядок CE/manual. Контрольные суммы
   сравниваются после каждой пары.
5. Измерение через ref_time_ticks/get_time_nsec охватывает только цикл работы.
   Компиляция, запуск процесса, прогрев и печать CSV находятся вне интервала.
6. Оба варианта вызываются через одинаковые block callbacks. Их общая стоимость
   входит в результат; это стоимость операции целиком, не отдельного Bind.

Runner сохраняет:

- `raw.log` — исходный вывод;
- `samples.csv` — все отдельные замеры;
- `summary.json` — медианы, диапазон CE, медиану попарных CE/manual отношений,
  режим, число операций, сведения о CPU/ОС и SHA-256 компилятора/исходников.

`CeNsPerOperation` и `ManualNsPerOperation` — медианы наносекунд на операцию.
`MedianPairedRatio` — медиана отношений соответствующих пар; она может немного
отличаться от отношения двух медиан. Значение 2 означает вдвое больше времени CE.

Heap проверяется до и после партии, уже после освобождения результатов.
Это проверка остаточной памяти, **не** число аллокаций и **не** пик памяти.
Нулевой delta не означает отсутствие временных выделений. Память строк живёт
по правилам контекста daScript и отдельно здесь не профилируется.

## Интерпретация

Сравнивайте режимы отдельно. Результаты интерпретатора нельзя переносить на JIT
или AOT. Оптимизатор вправе существенно упростить ручной код, особенно State
с небольшим фиксированным циклом; это часть измеряемой разницы, а не обещание
такого же коэффициента для произвольной программы.

Не запускайте тяжёлые тесты параллельно с бенчмарком. Для более уверенного вывода
повторяйте запуск отдельными процессами и увеличивайте число операций. Это
микробенчмарки одной машины, без доверительных интервалов и без гарантии
универсального ускорения/замедления. Async, scheduler, Writer с длинными строками,
ошибки native runtime и move-only коллекции не входят в эти сценарии.
