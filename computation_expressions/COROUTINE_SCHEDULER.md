# Планировщик корутин

`require coroutine_scheduler` подключает планировщик и CoroutineBuilder.
Для записи CE также нужен `require computation_macro`.

```das
var inscope scheduler:CoroutineScheduler
let id = coroutine_spawn(scheduler, npc())

// Один вызов за игровой кадр:
let running = coroutine_tick(scheduler)
let status = coroutine_status(scheduler, id)

// Отмена одной задачи или закрытие всего планировщика:
let cancelled = coroutine_cancel(scheduler, id)
coroutine_close(scheduler)
```

## API и владение

| Операция | Поведение |
|---|---|
| `coroutine_spawn(scheduler, source)` | Перемещает iterator в планировщик и возвращает CoroutineTaskId; тело не запускается |
| `coroutine_tick(scheduler)` | По одному resume каждой Running-задачи, в порядке регистрации; возвращает число оставшихся Running |
| `coroutine_status(scheduler, id)` | Running, Completed, Cancelled или Failed |
| `coroutine_error(scheduler, id)` | Сохранённое сообщение исключения для Failed; иначе пустая строка |
| `coroutine_cancel(scheduler, id)` | Закрывает Running-задачу; возвращает true, если она была активна, иначе false |
| `coroutine_close(scheduler)` | Отменяет все Running-задачи и запрещает новые регистрации; повторное закрытие безопасно |

ID теперь имеет тип `CoroutineTaskId {owner:uint64; slot:int; generation:uint64}` вместо int.
Код с `let id = coroutine_spawn(...)` менять не требуется; явно типизированные
поля и аргументы ID нужно перевести с int на CoroutineTaskId. Не передавайте
только поле slot: поколение обязательно для проверки актуальности.

Владелец ID проверяется: чужой, удалённый или устаревший ID вызывает panic в
status/error/cancel/forget. `coroutine_valid` возвращает false без исключения.
При перемещении планировщика его ID сохраняются. Новый планировщик получает
новый owner даже после удаления старого; owner не переиспользуется в пределах
одного daScript Context. Идентификаторы не предназначены для передачи между
Context, потоками, процессами или для сохранения на диск. При исчерпании owner
регистрация отклоняется, не допуская переполнения.

Spawn потребляет источник даже при отказе, например при закрытом планировщике:
источник закрывается, а вызывающий код получает panic. Переданная переменная
итератора после перемещения пуста. Планировщик сам является move-only значением.
Его можно перемещать вместе с задачами; копирование не поддерживается.

Удаление планировщика закрывает активные задачи и освобождает записи. Используйте
`var inscope` для обычного выхода из области или явный `delete`.
Для защиты от исключений внешнего игрового кода используйте `coroutine_scope`:

```das
coroutine_scope($(var scheduler:CoroutineScheduler) {
    let id = coroutine_spawn(scheduler, npc())
    let active = coroutine_tick(scheduler)
    // Остальной игровой цикл. Его panic тоже освобождает задачи.
})
```

Helper удаляет планировщик при нормальном выходе и при native panic, сохраняя
исходное сообщение исключения. Callback возвращает void. Если храните владельца
вне такого блока, закрывайте его явно в recover: native inscope не заменяет
защиту всех путей исключений в этой версии runtime. Пример —
`coroutine_scope_demo.das`.

## Статусы и ошибки

Running включает ещё не запущенные и ожидающие следующего кадра задачи.
Completed выставляется, когда resume вернул false; Cancelled — при отмене.
Native panic задачи становится Failed с сохранением сообщения. Её итератор
закрывается, затем tick продолжает оставшиеся задачи в том же кадре.
Завершённые задачи повторно не выполняются.

После coroutine_close статусы и ошибки остаются доступными. Tick закрытого
планировщика возвращает 0. Если освобождение при отмене бросило исключение,
записывается Failed вместо Cancelled; остальные задачи всё равно закрываются.
Тем не менее освобождающие функции должны быть небросающими: ограничения native
финализаторов из `COROUTINE.md` и `MOVE_RESOURCES.md` сохраняются.

Во время tick или освобождения нельзя вызывать spawn/cancel/close/tick для того
же планировщика. API отклоняет такой вызов, не меняя список. Если вызов сделан
из корутины и ошибка не перехвачена ею, она станет Failed. Запрос статуса допустим.
Прямое изменение полей или удаление исполняющегося планировщика недопустимо.
Отложенной очереди команд первой версии нет; изменения выполняет игровой цикл
между tick.

## Deferred и ограничения

`coroutine_spawn(scheduler, run_deferred(saved))` принимает независимый запуск
deferred-корутины. Сохранённое вычисление можно удалить после регистрации:
снимок каждого запуска остаётся жив до его завершения или отмены.

Планировщик однопоточный, без приоритетов и ограничения времени кадра. Корутина
без yield может блокировать весь tick. Семантика wait_frames не меняется:
каждый tick даёт активной задаче один resume.

## Удаление истории и повторное использование слотов

- `coroutine_forget(scheduler, id)` удаляет одну терминальную запись и возвращает
  true. Для Running возвращает false, не отменяя задачу.
- `coroutine_prune(scheduler)` удаляет все Completed/Cancelled/Failed-записи и
  возвращает их число. Running-задачи и их ID остаются прежними.
- `coroutine_task_count(scheduler)` — число сохранённых записей, включая историю.
- `coroutine_slot_count(scheduler)` — число выделенных слотов.

После forget/prune статус и ошибка удалённой записи недоступны. Сначала прочитайте
нужную диагностику. Освобождённый слот получает новое поколение при следующем
spawn; старый ID не может отменить занявшую его новую задачу. При исчерпании
uint64 поколений слот выводится из повторного использования вместо переполнения.

Tick и закрытие обходят сохранённые задачи в порядке регистрации независимо от
номеров повторно использованных слотов. Свободные слоты не входят в обход tick.
Поиск свободного места и удаление одной записи выполняются за O(1); tick/prune —
за O(число сохранённых записей). Буфер слотов не сжимается и сохраняет пиковый
размер до удаления планировщика. При регулярном prune и ограниченном числе
одновременно сохранённых задач количество слотов перестаёт расти. Неочищаемая
история по-прежнему занимает память. Освобождение памяти строк определяется runtime.

Forget/prune допустимы и после close, но не из callback во время tick/cleanup.
Эти операции не запускают задачи и не закрывают их повторно.

Пример переиспользования: `coroutine_slots_demo.das`. `test_coroutine_slots.das`
проверяет устаревшие ID, порядок после reuse, все позиции удаления, переполнение
поколения и стабильность памяти при 512 запусках в четырёх слотах.

Игровой пример: `coroutine_scheduler_demo.das`. Тесты:
`test_coroutine_scheduler.das` — порядок кадров, изоляция ошибки, отмена,
незапущенные задачи, перемещение владельца, break, отказы spawn, неверные ID,
повторный вход и освобождение памяти независимых deferred-запусков.


## Проверенный объём

Поддержаны ручной resume, планировщик кадров, дочерние сценарии, отмена,
изоляция ошибок задач, scope внешнего владельца, move-only ресурсы, deferred,
очистка истории и проверяемые owner/slot/generation ID. Все эти сценарии входят
в `../run.ps1 -Test`; проверки неверных программ также выполняются автоматически.

`test_coroutine_safety.das` дополнительно проверяет чужие ID, перемещение и
повторное создание владельца, все API-запреты повторного входа, очистку отклонённого
spawn и освобождение памяти при исключении внешнего игрового цикла.

Это завершённый кооперативный механизм кадров. Асинхронный I/O, многопоточность,
приоритеты, ожидания в секундах и очередь команд из задач в него не входят.
