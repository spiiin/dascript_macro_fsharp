# Сортировка, группировка и distinct

Операции доступны из `require ./lib/query_builder.das` как обычные функции с пайпами.
Они выполняются немедленно, заимствуют фиксированный или динамический входной
массив и возвращают новый владеющий массив. Исходные строки и их порядок не меняются.

| Операция | Результат |
|---|---|
| `source |> query_order_by(key)` | Стабильная сортировка по возрастанию ключа |
| `source |> query_order_by(key,true)` | По убыванию; равные ключи сохраняют исходный порядок |
| `source |> query_group_by(key)` | `array<tuple<key:K;values:array<T>>>` |
| `source |> query_distinct()` | Первое вхождение каждого значения, сравнение через `==` |
| `source |> query_distinct(key)` | Первая строка для каждого ключа |

Перегрузка `(source, descending, key)` позволяет ставить блок последним:

```das
var inscope ranking <- players |> query_order_by(true) <| $(p:Player) {return p.score}
var inscope ascending <- players |> query_order_by(false) <| $(p:Player) {return p.score}
// Без флага остаётся доступна сортировка по возрастанию:
var inscope defaultOrder <- players |> query_order_by <| $(p:Player) {return p.score}
```

Прежний порядок `(source, key, descending=false)` также поддерживается.
Перегрузка делегирует основному алгоритму без дополнительных массивов или
повторного вычисления ключей. Новый синтаксис допускает и `|> bind` после блока
внутри CE. Тесты сравнивают оба порядка аргументов и проверяют исключение ключа.

`key` — блок вида `$(row:Player) {return row.team}`. В каждой операции он вызывается
ровно один раз на входную строку, слева направо, включая строки, которые distinct
затем отбросит. Пустой вход не вызывает блок. Исключение прекращает обработку,
освобождает промежуточные массивы и передаётся наружу; эффекты блока не откатываются.

```das
var inscope ranking <- players |> query_order_by(true) <| $(p:Player) {return p.score}
var inscope champions <- ranking |> query_distinct <| $(p:Player) {return p.team}
```

В этом порядке `champions` содержит лучшего игрока каждой команды, при равном
счёте — первого во входе. Порядок групп и результат distinct определяется первым
появлением ключа. Внутри каждой группы строки идут в исходном порядке.

Группы владеют вложенными массивами. В CE их нужно явно связывать по ссылке:

```das
var inscope report <- computation(QueryBuilder(type<string>)) {
    var group & = players |> query_group_by <| $(p:Player) {return p.team} |> bind
    var total=0
    for(p in group.values) {total+=p.score}
    return "{group.key}: score={total}"
}
```

Такой bind потребляет массив групп и освобождает его после обхода или исключения
в продолжении. Если передать именованный массив групп, его владение тоже будет
передано. Ссылку на `group` или его элементы нельзя сохранять после завершения
продолжения. Для отсортированных строк и distinct используется обычный
`let row=source |> query_order_by(...) |> bind`.

Query по-прежнему требует копируемые выходные строки. Владение массивами групп
не означает поддержку произвольных move-only строк или ключей. Строки и ключи
этих операций должны быть копируемыми; для order_by нужен `<`, для группировки
и distinct — `==`. Порядок `<` должен быть согласованным (strict weak ordering),
а равенство ключей — отношением эквивалентности. Хеш-функция не нужна.

Сортировка использует стабильный merge sort: O(n log n), O(n) дополнительной
памяти. Group_by — O(n × g), где g — число групп; distinct — O(n × u), где u —
число уникальных ключей. В худшем случае обе операции O(n²). Это операции над
данными в памяти; индексов, SQL-трансляции и оптимизатора запросов нет.

В обычном коде сохраняйте каждый промежуточный динамический массив в отдельном
`var inscope`, как `ranking` и `champions` выше: функции заимствуют вход, поэтому
цепочка обычных вызовов с неименованными владеющими массивами не управляет их
временем жизни. Для CE временным источником управляет общий макропротокол.

Пример: [query_operators_demo.das](examples/query_operators_demo.das).
Тесты: [test_query_operators.das](tests/test_query_operators.das): стабильность
в обоих направлениях, однократное вычисление ключей и порядок эффектов, группы,
distinct, пустые/динамические входы, входные данные после вызова, пайповый bind,
исключения ключей и продолжения CE, отсутствие роста heap на 16 повторах после прогрева.

Эти четыре сценария также собраны и выполнены C++ AOT-хостом с

Остальной общий AOT-список в рамках изменения повторно не запускался.
Новый тест добавлен в `mode_tests.json`, а пример и тест — в

Блоки в конце `query_where`, `query_select`, `query_group_by` и ключевой перегрузки
`query_distinct` можно передавать через `<|`. Внутри CE после блока допустим
`|> bind`; для групп сохраняется `var group &`. Например:

```das
var inscope enabled <- players |> query_where <| $(p:Player) {return p.score>0}
var inscope scores <- enabled |> query_select <| $(p:Player) {return p.score}
```

`query_where(bool) |> bind` не содержит блока и сохраняет обычную запись;
`query_distinct()` без ключа тоже остаётся без `<|`. Вызовы `query_join` с двумя
блоками в примерах оставлены в прежнем виде. Скобочная запись всех операций
по-прежнему поддерживается и проверяется тестами на эквивалентность.

Обновление примеров на `<|`: `test_query`, `test_query_operators`, `query_demo`
и `query_operators_demo` прошли JIT без кеша. Они же вместе с
`test_domain_deferred` прошли интерпретатор и сборку/исполнение в строгом
AOT-хосте (`main->aot`, `fail_on_no_aot`): 5/5. Обновлённый экспорт проверен
отдельным приложением, использующим `<|` для всех четырёх операций.

Полная цепочка where → select → order_by → distinct → group_by с `<|`:
[query_full_demo.das](examples/query_full_demo.das). Пример проверяет каждый этап,
обе строки отчёта и сохранность результата после освобождения промежуточных
массивов. После прогрева выполняются 16 повторов с проверкой
`heap_bytes_allocated()` после выхода всех владельцев из области видимости.
Это проверка живого context heap массивов, а не всего процесса или string heap.
Пример включён в общий запуск, список JIT/AOT-generation и строгий AOT-хост.
Пайпы записаны на строке с источником: отдельная новая строка перед `|>` без
продолжения выражения в текущем синтаксисе daScript не принимается.

Полный пример проверен на SDK v0.6.5-RC2: interpreter, JIT без кеша и
исполнение в собранном C++ AOT-хосте со строгой линковкой. В этом AOT-прогоне
прошли 6/6 сценариев: три Query-примера, test_query, test_query_operators и
test_domain_deferred. Проверки отчёта и 16 повторов heap выполняются самим
query_full_demo в каждом режиме.
