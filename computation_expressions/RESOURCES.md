# Using / TryFinally: ресурсы в computation

Подключение прежнее: `require computation`.
Поддержаны все builders проекта, включая ListBuilder. Bind сохраняет синтаксис `|> bind`.

## Ресурс на время оставшейся части блока

```das
let outcome = computation(ResultBuilder()) {
    let loaded = open_document(text) |> bind
    let document = loaded |> use_resource
    // document доступен до конца текущей CE-области.
    return 42
}
```

`use_resource` — маркер макроса. Он приобретает ресурс ровно один раз и
превращает остаток текущей области в продолжение `ce_using`. По завершении
продолжения вызывает `ce_dispose` для приобретённого ресурса. Нужна перегрузка
в модуле ресурса, доступная вызывающему коду:

```das
def ce_dispose(var resource : MyResource) {
    close_handle(resource.handle)
}
```

Перегрузки по умолчанию нет: отсутствие disposer — ошибка компиляции.
Cleanup-callback генерируется в вызывающем модуле, где видна его перегрузка.
При Result/Option приобретении сначала используйте обычный bind, затем
use_resource. При Error/None в приобретении ресурс не передаётся в Using и
не освобождается им. Функция приобретения сама отвечает за частичные
выделения до своего неудачного завершения.

Два последовательных ресурса освобождаются в обратном порядке. Ресурс внутри
тела for/while освобождается в каждой достигнутой итерации. Ресурс внутри ветки
освобождается до продолжения после ветки. При остановке цепочки ещё не достигнутые
приобретения не вычисляются.

## Произвольная очистка через TryFinally

```das
let outcome = computation(ResultBuilder()) {
    try_finally($ {
        let n = checked_operation() |> bind
        return n + 1
    }, $ {
        record_scope_exit()
    })
}
```

Первый блок — CE-область: поддерживает bind, ветки, циклы, use_resource и return.
Второй блок — обычный daScript block без аргументов с результатом void.
Он вызывается ровно один раз после завершения первого блока. Он видит внешние
переменные, но не локальные переменные, объявленные только внутри первого блока.
Для ресурса, приобретаемого внутри первого блока, используйте use_resource.

`try_finally` записывается отдельной инструкцией CE. В завершающей позиции
он возвращает результат первого блока. Если далее есть другие инструкции,
первый блок должен вычислять Unit и объединяется с продолжением через Combine.
Для присваивания результата такой области переменной используйте вложенную
computation. Маркеры bind/use_resource внутри cleanup не обрабатываются;
это обычная синхронная очистка, не отдельный канал Result/Option.

Нативная запись `computation(...) { ... } finally { ... }` по-прежнему
отклоняется. У неё другое размещение локальных переменных после CPS-преобразования;
для CE используется явный `try_finally(body, cleanup)`.

## Успех, Error/None и исключения

Error и None — обычные возвращаемые значения. Using и TryFinally выполняют
очистку и возвращают результат без изменений. Журнал WriterResult сохраняется,
StateResult сохраняет откат к исходному состоянию. Очистка сама по себе не
добавляет записи в Writer и не меняет уже сформированный Result.

На установленном Daslang 0.6.4 обычный нативный finally не выполнился при
panic, перехваченном внешним recover. Поэтому runtime-обёртки явно используют
try/recover: сохраняют сообщение, вызывают cleanup и снова вызывают panic.
Сообщение сохраняется, но это повторный panic: место возникновения/стек могут
указывать на runtime-обёртку. Исключение не преобразуется в Error или None.
Откат StateResult по-прежнему гарантируется для Error, не для panic.

Вызов cleanup на нормальном пути находится вне защищённого try, поэтому его
собственный panic не приводит к повторной очистке. Если cleanup падает при
обработке уже возникшего panic, ошибка cleanup заменяет исходную ошибку;
внешние области продолжают своё освобождение. По возможности disposer должен
быть коротким и не бросать исключений.

Аварийное завершение процесса и нативные сбои не являются поддержанным путём
размотки. Гарантия относится к нормальному возврату, Error/None и перехватываемому
panic daScript, проверенному тестами.

## Владение и ограничения

Для `let resource = source |> use_resource` используются копируемые обёртки. Using владеет приобретённым
handle; переменная в теле — заимствованная копия. Не возвращайте её наружу,
не сохраняйте за пределами области, не освобождайте вручную и не передавайте
тот же handle второму Using. Эти правила пока не проверяются статически.
Не заменяйте handle в заимствованной копии: освобождается исходный ресурс.
Move-only владение поддержано через `var resource & = source |> use_resource`;
контракт единственного disposer и время жизни ссылки описаны в
[MOVE_RESOURCES.md](MOVE_RESOURCES.md). Асинхронного dispose нет.

В `json_resource_example.das` JsonResource хранит const-указатель на дерево
JSON. Только disposer снимает const в unsafe-блоке для вызова delete_json;
он освобождает именно дерево, которым владеет ресурс. Заимствованные указатели
на узлы не должны переживать область Using. Это граница владения примером,
а не общая возможность безопасно удалять произвольные const-указатели.

## Пример и проверки

`resources_demo.das` читает реальный JSON-документ, затем проходит успешный и
ошибочный путь. Счётчики подтверждают `opened=2, closed=2, finally=2`.
Некорректный JSON проверяет неудачное приобретение без вызова disposer.

```powershell
cd C:\src\dascript_macro_fsharp\computation_expressions
.\run_computation.ps1 -Test
```

`test_computation_resources.das` проверяет все builders, порядок LIFO,
единственное приобретение/освобождение, пустые области, ресурсы в циклах,
Error/None до и после приобретения, пропуск последующих шагов, вложенные
области, сообщения исключений, panic тела, сбой приобретения и disposer,
сбой cleanup без повторного вызова, журнал WriterResult и откат StateResult.

Негативные тесты проверяют отсутствие ce_dispose, ненулевой результат cleanup,
неверные аргументы try_finally и use_resource без объявления переменной.
`../run.ps1 -Test` включает все проверки. Реализация: `computation_resources.das`
(runtime) и новые преобразования маркеров в `computation.das`.

Ресурсы при многократном вызове продолжения ListBuilder проверяются в `test_list.das`; см. [LIST.md](LIST.md).


## SequenceBuilder

Ленивые ресурсные области поддержаны отдельно: `SEQUENCE_RESOURCES.md`.
Они освобождают ресурсы при завершении, break и ошибке вычисления. Для ошибок
в обработчике потребителя используется `sequence_each`. Захваты cleanup
хранятся в lambda, а не в стековом блоке; ограничения описаны в документе.
