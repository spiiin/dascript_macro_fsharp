# Ресурсы в SequenceBuilder

Подключение: `require computation`. Пример с реальным JSON-документом:
`sequence_resources_demo.das`. Проверки: `test_sequence_resource.das`.

```das
var inscope values <- computation(SequenceBuilder()) {
    let resource = acquire() |> use_resource
    try_finally($ {
        yield read_value(resource)
        yield read_next_value(resource)
    }, $ {
        print("scope finished\n")
    })
}
for (value in values) {
    print("{value}\n")
    break
}
// cleanup завершён и ce_dispose(resource) уже вызван.
```

Нужна доступная вызывающему модулю перегрузка
`def ce_dispose(var resource : MyResource)`. Для обычного let-объявления
дескриптор должен быть копируемым. Move-only ресурсы поддержаны через
`var resource & = acquire() |> use_resource`: см. [MOVE_RESOURCES.md](MOVE_RESOURCES.md);
как и в остальных builders, нельзя самостоятельно закрывать, переоформлять
владение или сохранять ресурс за пределами его области.

## Срок жизни

Ресурс приобретается при достижении use_resource во время обхода, а не при
создании iterator. Не начатая последовательность ничего не открывает и не
выполняет cleanup. Ресурс остаётся открыт между yield и закрывается после
оставшейся части текущей области. В цикле ресурс открывается и закрывается
для каждой достигнутой итерации. Ресурс перед bind живёт до окончания всех
его продолжений; ресурс после bind принадлежит отдельному продолжению.

try_finally принимает два блока без аргументов: тело CE и обычный блок очистки
с результатом void. Тело может выдавать значения. Очистка выполняется один раз
при завершении этой области, включая пустое тело. Вложенные области закрываются
в обратном порядке. Очистка завершившейся области происходит до последующих
инструкций CE, а не откладывается до конца всей последовательности.

Проверены полный обход, break, return из функции-потребителя, явное закрытие
после одного next, panic/assert из тела вычисления и ошибка приобретения
следующего ресурса. При ошибке приобретения закрываются ранее приобретённые
ресурсы. Если cleanup сам бросает ошибку, внешние cleanup также вызываются;
ошибка cleanup заменяет исходную. Сообщение ошибки сохраняется, место повторного
panic/стек могут отличаться от исходного.

## Ошибка потребителя

Ошибка внутри SequenceBuilder перехватывается автоматически. Ошибка внутри
тела внешнего native for находится за пределами генератора: daScript 0.6.4
не гарантирует закрытие итератора при таком исключении. Для такого потребителя
используйте обход, который владеет итератором:

```das
var inscope values <- make_values()
sequence_each(values, $(value : int) {
    process(value) // может бросить panic
})
```

sequence_each закрывает последовательность и при успехе, и при ошибке
обработчика. Она однопроходная и после обхода закрыта. Для ручного next можно
вызвать `sequence_close(values)`; повторное закрытие пустого iterator безопасно.
Native for с обычным break поддерживается напрямую.

## Захваты и реализация

Каждая ресурсная область владеет дочерним iterator и хранимой cleanup lambda.
Сначала закрывается дочерний iterator, затем вызывается cleanup. Стековые
callbacks не сохраняются за пределами вызова. use_resource передаёт cleanup
снимок дескриптора, а тело использует заимствованную копию того же дескриптора.

Локальные `var`, объявленные **внутри SequenceBuilder**, теперь используют общие
ячейки, если вычисление содержит ресурсные области. Изменения видны в теле,
cleanup и продолжении после области. Поддержаны копируемые скаляры и структуры,
`var x = source |> bind`, инициализация по умолчанию и явные типы.

```das
var inscope values <- computation(SequenceBuilder()) {
    var n = 1
    try_finally($ {
        n = 2
        yield n
    }, $ {
        print("cleanup sees {n}\n") // 2
        n = 3
    })
    yield n // 3
}
```

Ячейка принадлежит области объявления переменной. Сначала выполняются все
вложенные cleanup, затем освобождается ячейка. При break и ошибке порядок тот
же. Переменные внутри итерации получают отдельные ячейки; завершённые итерации
не удерживают их до конца последовательности. Тест на 1000 итераций проверяет
постоянный объём живой памяти и возврат к исходному объёму после закрытия.

Одноимённые вложенные переменные, параметры блоков и переменные for сохраняют
свои собственные значения: подстановка учитывает лексическую область видимости.
Тип и выражение инициализации исходного var сохраняются; выражение выполняется
один раз. Для SequenceBuilder без ресурсных областей преобразование не применяется.
Цена общей ячейки — выделение памяти и дополнительная ресурсная область на var.

Граница поддержки: внешние переменные, объявленные **до** computation, остаются
обычными захватами native generator по значению. Сам макрос не меняет их время
жизни. Произвольные локальные explicit-reference, inscope, move/clone объявления
не входят в преобразование общих ячеек для копируемых var. При этом специальные
CE-привязки `var item & = source |> bind`, move-only `yield <-` и
`var resource & = source |> use_resource` поддерживаются своими путями;
см. [MOVE_COLLECTIONS.md](MOVE_COLLECTIONS.md) и [MOVE_RESOURCES.md](MOVE_RESOURCES.md). Адреса ячеек и ресурсы нельзя
сохранять за пределами их области. Неявные внешние move-only захваты по-прежнему
требуют отдельного интерфейса.

Пример: `sequence_shared_demo.das`; проверки: `test_sequence_shared.das` и
`test_sequence_shared_lifetime.das`.

В runtime 0.6.4 есть два проверенных ограничения: yield внутри try/recover
не возобновляется корректно; финализатор вызывается с установленным флагом
break/return. Поэтому перехват находится вокруг next, а вход в финализатор
использует локальный служебный panic/recover для сброса флага. LambdaIterator
сам сохраняет и восстанавливает внешний флаг. Это добавляет накладные расходы
и меняет диагностическое last_exception при успешной очистке; это поле не
следует использовать как признак неудачного обхода.

Ресурсные гарантии рассчитаны на перехватываемые ошибки daScript. Завершение
процесса и повреждение native runtime не обеспечивают выполнение cleanup.

Проверки запускаются через `run_computation.ps1 -Test` или общую `../run.ps1 -Test`.



Обработать исключение внутри CE теперь можно через `try_with`: правила очистки
до входа в обработчик и ленивого восстановления описаны в `TRY_WITH.md`.

Вложенные iterator-источники `for`, `bind` и `yield_from` имеют отдельную
защиту закрытия: [SEQUENCE_NESTED_CLEANUP.md](SEQUENCE_NESTED_CLEANUP.md).
Пример: `sequence_nested_cleanup_demo.das`.
