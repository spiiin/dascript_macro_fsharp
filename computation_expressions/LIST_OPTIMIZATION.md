# Оптимизация ListBuilder

## Что изменилось

Линейная цепочка из двух и более обычных bind, заканчивающаяся return,
теперь может писать непосредственно в один итоговый массив. Источники
перечисляются вложенными вызовами в прежнем порядке; второй источник
вычисляется заново для каждого элемента первого, а не заранее.
Пайповый синтаксис не меняется:

```das
var inscope values <- computation(ListBuilder()) {
    let a = fixed_array(1,2,3,4) |> bind
    let b = fixed_array(10,20,30,40) |> bind
    return a*b
}
```

Пример: list_fusion_demo.das. До: внешний результат ce_bind плюс отдельный
результат ce_list_map для каждого a. После: один накопитель ce_collect_into.
Поддержаны цепочки большей длины и bind без переменной.

Для одиночного consuming bind (var item & = source |> bind) с финальным
return/return <- результат тоже собирается напрямую. В move-only варианте
исчезают массивы из одного элемента, которые прежде создавал каждый return <-.
Исходный массив передаётся во владение, его элементы заимствуются продолжением.
При ошибке накопленный результат удаляется перед оставшимся входом.

## Сохранение семантики и границы

- Промежуточные локальные инструкции, ветвления, циклы, yield, return_from,
  and_bind и ресурсные области сохраняют прежнее раскрытие. Отдельная
  подходящая цепочка внутри такой области может быть оптимизирована.
- Несколько consuming bind не объединяются в один буфер. Это сохраняет
  границы владения и порядок очистки разных уровней при исключениях.
- Типы результата с пользовательским finalize, включая вложенные поля и
  контейнеры, используют прежний путь. Иначе исчезновение moved-from ячеек
  меняло бы число вызовов финализатора даже при отсутствии утечек.
- Классы, указатели, внешние handle, iterator/lambda и слишком глубокие типы
  также консервативно оставлены на прежнем пути. Пользовательский finalize
  массива или generic finalize в программе отключает слияние целиком: число
  финализаций промежуточных массивов может быть наблюдаемым эффектом.
- Обычные move-only структуры с массивами без пользовательского finalize
  поддержаны. Это проверяется отдельно от ветки с наблюдаемыми финализаторами.

Сокращаются промежуточные **массивы результатов**. Массивы, создаваемые самими
источниками, сохраняются. Единственный итоговый массив по-прежнему может
несколько раз увеличивать ёмкость; число выделений памяти здесь не измерялось.

## Протокол и реализация

Новый необязательный ce_collect_sink(builder) возвращает
ce_collect_sink_protocol(type<T>). По умолчанию возвращается
CeCollectSinkFallback, поэтому чужие builders не меняют поведение.
Дескриптор проверяется только по типу и не выполняется в runtime.
Слияние опирается на ce_collect_into, ce_collect_each/ce_collect_each_move
и ce_collect_emit/ce_collect_emit_move. Стратегии Value/Collect/Owned/Sequence
не заменяются; это опциональный путь внутри прежнего раскрытия.

Проверка типа результата и финализаторов выполняется при компиляции.
Runtime-проверок типа и runtime-проверки возможности оптимизации нет.
Для собственного builder опциональные операции должны реализовывать именно
контракт непосредственного накопления в array<T>, синхронного обхода и cleanup;
одного дескриптора для произвольного Collect builder недостаточно.

## Раскрытие и тесты

Команда: `daslang.exe examples/list_fusion_demo.das -no-module-cache -log`.
[Раскрытие до](list_expansion_before.txt) и [после](list_expansion_after.txt).
Runner проверяет присутствие ce_collect_into и отсутствие старых
ce_bind/ce_return/ce_list_map в раскрытии этого примера.

test_list_fusion.das сравнивает быстрый путь с тем же CE, где дополнительное
локальное объявление сохраняет прежнее раскрытие. Проверяются зависимый второй
источник, изменения входа из mapper, пустые источники, исключения, цепочка из
трёх bind, consuming-map, вложенное владение и полный журнал пользовательских
финализаторов — в том числе финализация уже перемещённых пустых объектов.
Для быстрого move-only пути отдельно проверяется возврат heap к исходному
значению при ошибке на каждой позиции. test_list_benchmarks.das проверяет
равенство контрольных сумм CE/manual для всех 64 входов и остаточную память.

## Бенчмарки

```powershell
./run_list_benchmarks.ps1 -Iterations 30000 -Samples 9
./run_list_benchmarks.ps1 -Jit -Iterations 30000 -Samples 9 -OutputDirectory ./list-benchmark-jit
```

list_product — прежнее произведение 4×4. list_variable использует массивы
длины seed%9 и seed%13, включая пустые. list_owned передаёт владение списком
из seed%15+1 элементов, каждый из которых владеет array<int>. В ручном коде
сохраняются те же источники, порядок результатов, полезная работа и освобождение.

По 9 партий из 30000 операций; прогрев 1000, чередование CE/manual.
Компиляция и печать исключены из таймера. До/после измерялись последовательно,
без параллельного запуска наших тестов. Остальная методика — BENCHMARKS.md.
Обе версии бенчмарка используют одинаковые исходники workloads.
Для воспроизведения версии до в отдельной копии проекта замените три файла
их сохранёнными list_before_*.das.txt. Хеши компилятора и исходников — в JSON.

## Интерпретация

На этих сценариях расходы уменьшились в обоих режимах. Особенно заметен
выигрыш JIT на фиксированном произведении, однако CE всё ещё дороже ручного кода.
Это одна машина и один набор партий; времена ручной стороны также колеблются.
Точные универсальные коэффициенты ускорения и доверительные интервалы
из этих данных не следуют. AOT, пик heap и число аллокаций не измерялись.

Временных порогов в тестах нет. JIT-проверка эквивалентности workloads
проходит. Обработка native panic под JIT в целом имеет известные ограничения
этого bundle (см. STATE_OPTIMIZATION.md); эти бенчмарки не проверяют её.
